PhysioQC

A Python tool for explainable, windowed quality checks on physiological recordings. Each flag stays attached to its channel, sample bounds, metric values, parameters, and source provenance—so a reviewer can inspect the evidence instead of inheriting an unexplained score.

Why quality control needs more than a score

A flatline, clipping, line interference, and a burst can all make a segment hard to use, but they point to different causes. A weighted composite can be useful for triage; it can also hide whether a high score came from a disconnected electrode, a brief transient, or a threshold that does not fit this modality. PhysioQC currently emits explicit flag reasons and does not collapse them into an opaque composite.

What one record carries

Output is one record per channel and window. Alongside the metrics, it stores the source file name and SHA-256, sample interval, nominal duration, sampling rate, full metric configuration and its hash, schema/software version, computation time, explicit flags, and a stable window ID. That context makes it possible to rerun a decision or compare outputs made with different thresholds.

{
  "record_type": "window_qc",
  "window_id": "a47c…-000004-ECG_II",
  "sample_start": 1000,
  "sample_end_exclusive": 1250,
  "metrics": {"rms": 0.18, "flatline_fraction": 0.0, "clip_fraction": 0.0},
  "quality_flags": [],
  "source_sha256": "…",
  "config_sha256": "…"
}

Review is a second record, not an overwrite

A machine-generated candidate and a reviewer’s judgment answer different questions. The annotate command appends a separate record with a label, reviewer, note, and timestamp. This means a threshold can change while the original review remains intact, and a reviewer can disagree with a flag without erasing why the flag appeared.

Window length and overlap are analysis choices, too. Short windows localize a brief problem but can make spectral estimates unstable; long windows smooth over transitions. The record boundaries are therefore explicit. The current CLI processes non-overlapping windows; overlap remains an explicit next extension.

Runnable synthetic study

The included demo generator writes seven synthetic channels: clean oscillation plus noise, injected mains interference, a flatline interval, slow drift, bursts, clipping, and missing samples. It is useful for exercising edge cases and reading the output schema. It is not a clinical benchmark, and it does not establish sensitivity or specificity on real EEG, ECG, EMG, or PSG.

python demo.py --output demo.csv
python physioqc.py run demo.csv --sample-rate 250 --window-seconds 10 \\
  --clip-abs 2.5 --signal-band 0.5,40 --output qc.jsonl
python physioqc.py annotate --window-id WINDOW_ID --label review \\
  --reviewer binoy --note "inspect transition" --output annotations.jsonl

CSV is read one window at a time, so working memory scales with window size rather than the full recording. JSONL is the default. The optional Parquet conversion writes bounded batches through PyArrow. Batch input and configuration are hashed for provenance; live records keep a stable configuration hash and identify their transport source.

Live input and watched-folder processing

The listen command accepts newline-delimited JSON sample frames over TCP or a Unix-domain socket; the default TCP address is loopback. listen-shm consumes a documented single-writer shared-memory ring with sequence markers and explicit overrun reporting. The foreground daemon watches an inbox, waits for a CSV to stabilize, then processes each content hash once and records state for restarts.

Review, BIDS metadata, and evaluation

The curses-based tui moves through QC windows and appends usable, artifact, or review annotations with an optional note. BIDS JSON sidecars can supply sampling and power-line frequency metadata and help infer modality. The offline evaluate command compares event candidates to independent window labels and reports confusion counts, precision, recall, specificity, and F1.

EEG, ECG, EMG, and PSG profiles are exploratory starting points and marked exploratory_unvalidated in output. A sidecar can be selected explicitly or discovered beside a CSV. The prototype does not resolve BIDS inheritance or read BIDS TSV recordings directly.

What I would validate before trusting it

First, controlled faults with known locations and amplitudes: line noise just inside and outside the configured band, flatline spans of different lengths, injected steps and ramps, saturation near the ADC rail, and missing blocks. Then reviewer-labeled real segments across recording setups. I would report false alarms and missed intervals by fault type, with thresholds fixed before evaluation, and examine whether unusual but valid physiology is being flagged. One aggregate score would obscure exactly the failure modes I want to see.

Implemented: bounded CSV processing; TCP, Unix-socket, and shared-memory input; watched-folder daemon; terminal annotation; sidecar parsing; exploratory modality profiles; JSONL and optional batched Parquet; provenance; and a window-level evaluation harness.

Still unvalidated: real-world clinical performance, adjudicated thresholds, modality-specific validated defaults, and BIDS inheritance/direct TSV ingestion. The evaluation command is ready for labeled data, but this project includes only synthetic examples, so no sensitivity, specificity, or clinical-use claim is made.
