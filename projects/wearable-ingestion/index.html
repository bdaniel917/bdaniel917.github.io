PLATFORM STUDY · DIGITAL HEALTH

Digital Health Wearable Pipeline

A study-agnostic intake layer for pharma and digital-health research: accept data from multiple wearable sources, preserve the original payload, route work through a durable queue, and process it in the cloud without making every study reinvent its own ingestion script.

This grew out of hands-on work with multimodal wearable data and the recurring engineering burden around it: different devices, file formats, rates, identifiers, and delivery patterns arriving across studies. The project separates what should be reusable across studies from the study-specific decisions that still need clinical and scientific ownership.

The system should outlive a study

A single study can get by with a notebook and a folder of exports. The pressure changes when a team is collecting from many participants, across devices, vendors, protocols, and studies at once. A useful shared layer should make source-specific integrations replaceable while keeping study identity, participant mapping, consent state, and analysis rules explicit.

The design has two planes. The control plane holds study configuration, source mappings, participant pseudonyms, consent/access policy, and transformation versions. The data plane accepts payloads, stores raw bytes, schedules processing, and writes derived outputs. Keeping them distinct makes it easier to change a study rule without rewriting the raw data or confusing provider identifiers with a research identity.

Why queue before doing expensive work?

Ingress should acknowledge a valid event quickly and hand the payload reference to a durable queue. Workers can then scale separately from the request endpoint, retry transient failures, and process large backfills without keeping a webhook request open. Every retry must be idempotent: the same event should not silently create a second session or duplicate a derived partition.

Raw payloads stay intact so a parser fix can replay them. Derived records carry their processing version and source hash. A late-arriving file, a duplicate event, a revoked connection, and a changed schema are expected operating conditions—not exceptional cases to hide in logs.

A cloud mapping I would test

On AWS, one plausible arrangement is a small authenticated ingress service, SQS for durable work, S3 for immutable raw and versioned derived objects, containerized workers for parsing/QC, and Databricks for study-wide analysis. The worker pool can scale independently of data collection. The point is not a particular cloud product; it is that expensive processing happens beside the stored data, while the study team gets versioned, queryable outputs.

Provider APIs such as Terra’s documented Destinations can sit behind an adapter boundary. A webhook or provider event should become a normalized event envelope, then enter the same ingestion path. Terra documents event references for relating requests to asynchronous events; those IDs are useful for idempotency and transfer reconciliation. This prototype does not connect to Terra or fetch provider payloads. A real adapter would need authenticated webhook handling, secure credential management, provider-to-study identity mapping, and payload retrieval/verification.

The runnable part

I built a local Python reference prototype to make the contracts testable without cloud credentials. It accepts an event envelope and a timestamped CSV, stores the raw file by SHA-256 under tenant/study/participant/session/stream partitions, and writes a SQLite job record with a unique provider/event key. Re-ingesting the same event is idempotent. A local worker validates rows, retains malformed-row counts, and writes a canonical long-form CSV and processing summary.

python pipeline.py ingest --root ./demo-lake \\
  --event sample-event.json --data sample-stream.csv
python pipeline.py work --root ./demo-lake
python pipeline.py status --root ./demo-lake

The sample contains synthetic ECG and accelerometry columns. Tests cover duplicate delivery, malformed timestamps, and identifier path traversal. Failed jobs can be requeued with retry after a parser or configuration fix. The local filesystem and SQLite catalog are stand-ins for object storage and a cloud queue; the architecture above is a design proposal, not deployed infrastructure.

Where the hard questions remain

01

How do sources define time?

Preserve source timestamps and units; distinguish event time from arrival time; record gaps and clock assumptions before any resampling.

02

What does “normalized” mean?

Canonical storage should not flatten clinically meaningful differences between sleep summaries, activity events, and high-rate ECG samples.

03

How do study boundaries hold?

Tenant isolation, least-privilege access, consent changes, audit history, retention, and deletion behavior need to be designed and tested—not inferred from folder names.

04

Can an old result be reconstructed?

Keep original bytes, parser version, configuration, event lineage, and checksums so changes in code do not rewrite the historical account.

Scope and honesty. The repo contains a runnable local ingestion prototype and synthetic fixtures. It does not implement cloud resources, production security, a live Terra connector, PHI handling, a validated clinical data model, or compliance controls. Those would be the next engineering phase; the prototype is not a production clinical platform.
